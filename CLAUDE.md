# Localo — Project Guide

This file is auto-loaded at the start of every session. Read it first to understand the whole project, then dive into the files it points to.

## What the app is

**Localo** is a local business directory + marketplace (Expo / React Native). Anyone can browse businesses around them; anyone signed in can list one. A "business" is generic — it covers four **listing types**:

- **service** — a service provider (e.g. "Arvind Transport Services")
- **shop** — an ongoing shop selling goods (cafe, restaurant, bakery, handcrafts…); shops can have a **menu**
- **item** — an individual's **personal stall**: ONE listing per user that holds everything they're selling as `products` (their phone AND their car live in the same stall). Auto-created on their first item as "‹Name›'s Stall" (`defaultStallName` in catalog.ts, renameable in Manage); each product carries its own `subcategoryId` so the **Stalls** browse tile's chips filter by what's inside the stall.
- **rental** — something rented out (flat, car, bike, furniture…)

Businesses have a **team hierarchy** (owner → managers → staff), can receive **customer chats** and **calls**, and customers get **notifications** when a business replies.

## Tech stack

- **Expo SDK 57** (`react-native` 0.86, React 19). IMPORTANT: Expo changed a lot — check the exact v57 docs (see AGENTS.md) before writing Expo code.
- **expo-router** (file-based routing; `main` is `expo-router/entry`). Typed routes are ON (`app.json` → `experiments.typedRoutes`).
- **TypeScript**, strict. Path alias `@/*` → `src/*`.
- **expo-linear-gradient** for gradient UI.
- No state library — React state + a small `useAsync` hook. No real backend yet (see Data layer).

## Architecture (designed for easy change)

Layers, each folder has a single job:

```
src/
  app/            # Routes ONLY (expo-router). See "Routes" below.
  domain/         # types.ts (entities) + catalog.ts (4 internal types, as data) + tags.ts (discovery tags) + intents.ts (customer browse categories) + modules.ts (workspace modules) + geoCatalog.ts (city/state typeahead data)
  data/           # repositories.ts (interfaces) + DataProvider.tsx (context/hooks) + mock/ (in-memory impl + seed)
  features/       # Composed feature UI: businesses/, billing/, calls/, chat/, employees/, orders/
  components/ui/  # Reusable primitives (barrel export at components/ui/index.ts)
  theme/          # theme.ts — all design tokens (colors, spacing, radius, fontSize)
  lib/            # useAsync.ts, geo.ts (haversine), money.ts (parsePrice/formatMoney), share.ts (share sheet)
```

**The golden rule: screens depend on repository *interfaces*, never on a concrete backend.**
- All data access goes through `useRepositories()` / `useAuth()` from `@/data/DataProvider`.
- Interfaces live in `src/data/repositories.ts`: `BusinessRepository`, `EmployeeRepository`, `UserRepository`, `AuthRepository`, `PlacesRepository`, `ChatRepository`, `NotificationRepository`, `BookingRepository`, `OrderRepository`, `BillRepository`, `CallRepository`, `CustomerRepository`, `TrackingRepository`, `ReviewRepository`, `ProductThreadRepository`.
- They're currently backed by **in-memory mocks** in `src/data/mock/mockRepositories.ts`, seeded from `src/data/mock/seed.ts`.
- **To move to a real backend**: implement the same interfaces and change the ONE selector in `DataProvider.tsx`. Nothing else changes.

## Backends — TWO of them, one shared frontend

Localo deliberately supports **two interchangeable real backends** behind the same `Repositories` interfaces, chosen by an env var so the whole app can switch providers in one line. The frontend (every screen, `src/data/repositories.ts`, `src/domain/types.ts`) is IDENTICAL for both. There are three repository implementations:

1. **mock** — `src/data/mock/mockRepositories.ts`. In-memory, dev/offline. **This is the behavioural spec** both real backends must match method-for-method (it holds all the real logic: order proposals/dine-in tabs/`moveToBilling`, membership billing-cycle math + payment summaries, customer aggregation, review eligibility, call state machine, tracking, stall folding, etc.).
2. **supabase** (Path A) — `src/data/supabase/`. App talks straight to Supabase (Postgres + Auth + RLS + auto REST). Built so far: `auth` + `users`; the rest still delegate to the mock via `createSupabaseRepositories()` (a mock set with the migrated repos layered on). Schema + RLS live in `supabase/migrations/` (**document model**: every table is `data jsonb` = the full domain object + scoping columns owner_id/customer_id/business_id/… that RLS keys on).
3. **api** (Path B) — **BUILT.** A custom **Node/Express + Prisma** server in `backend/` plus a frontend HTTP client `src/data/api/` implementing the same interfaces via `fetch`. This is the "routers → services" backend (thin routers with authz guards; logic in `backend/src/services/`, a faithful port of the mock). ALL 18 repositories are implemented except `places` (device GPS — client-side, like Path A). Swagger at `/docs`. Selected by `EXPO_PUBLIC_BACKEND=api` (+ `EXPO_PUBLIC_API_URL`). See `backend/README.md`.

**The switch** (to wire in `DataProvider.tsx` when Path B lands): `.env` → `EXPO_PUBLIC_BACKEND=supabase|api|mock`. Path B also needs `EXPO_PUBLIC_API_URL`. (Today `DataProvider` just auto-picks supabase when `isSupabaseConfigured`; generalise it to read `EXPO_PUBLIC_BACKEND`.)

**⚠️ STANDING RULE — keep BOTH backends in sync.** Any change to data behaviour (a new repository method, changed logic, a new field) MUST be made in BOTH real backends and kept behaviour-identical to the interface + mock: (a) the Supabase repos in `src/data/supabase/`, AND (b) the Express controllers in `backend/` + the HTTP client in `src/data/api/`. Never migrate/patch one and forget the other.

When Sagar says **"create the backend"** (or similar), build the ENTIRE Node/Express + Prisma backend (Path B) implementing everything the app currently does. Do NOT ask him to re-supply context — it all lives in the repo + this file. Plan:

- **Stack:** Node + Express + Prisma, **TypeScript**. Structure: `routers → controllers → services`; **Swagger/OpenAPI** docs; folder `backend/` in this repo (monorepo, deploys independently, e.g. to Render — co-locate its region with the Supabase DB; free tier cold-starts).
- **Database — SAME Supabase Postgres as Path A** (both backends share one DB; project ref `mzxslzouzmiswnrolcaq`, direct connection string). Reuse the **document-model tables** in `supabase/migrations/`. Prisma maps each table as `{ id, <scoping cols>, data: Json, createdAt }`. **The SQL migrations stay the schema source of truth** (they own RLS + triggers); Prisma uses `prisma db pull` to introspect them into a typed client — do NOT run two migration tools against one DB. Connect Prisma with a privileged/direct connection (bypasses RLS — the backend enforces access itself, see Authorization).
- **Auth — reuse Supabase Auth for identity** (don't hand-roll password storage; Supabase already hashes/manages it, and `profiles.id` FKs to `auth.users`). Frontend logs in via Supabase → gets a JWT → sends `Authorization: Bearer <jwt>` to the Express API → backend verifies it with the project's JWT secret/JWKS → resolves the user id. `AuthRepository` on the api client wraps the same Supabase sign-in/up but points reads at the API.
- **Authorization — reimplement the RLS rules as controller/middleware checks.** `supabase/migrations/0002_policies.sql` is the authz spec: e.g. `isBusinessMember(businessId, userId)` = owner or employee; customer-or-member on orders/bills/bookings/chats/calls/memberships; recipient-only on notifications; public read on businesses/employees/reviews/product threads; author-only writes on reviews/product messages. Roles in play: guest, signed-in customer, business owner, manager, staff (+ per-tool `Employee.permissions` from `domain/access.ts`).
- **What to implement:** EVERY method of EVERY interface in `src/data/repositories.ts` (all 18 repositories), matching `src/data/mock/mockRepositories.ts` behaviour exactly. Domain shapes: `src/domain/types.ts`.
- **API shape:** one REST resource group per repository; endpoints map 1:1 to interface methods and return the SAME domain objects the interfaces specify (so `src/data/api/` passes them straight through). Document every route in Swagger.
- **Frontend client `src/data/api/`:** implement the `Repositories` interfaces with `fetch` to the Express endpoints (attach the Supabase JWT). `createApiRepositories()` returns the set; `DataProvider` selects it when `EXPO_PUBLIC_BACKEND=api`.
- **Verify:** app — `npx tsc --noEmit` + `npx expo export --platform web`. Backend — its own typecheck/build, Swagger serving, and a smoke test (sign in → create business → list) end-to-end with `EXPO_PUBLIC_BACKEND=api`.

## Domain model (`src/domain/types.ts`)

- `ListingType` = 'service' | 'shop' | 'item' | 'rental'. `ListingTypeDef` (in catalog) has label/singular/icon/color/actionLabel/subcategories.
- `Business` — generic listing: `type`, `subcategoryId`, `location` (with privacy), `employeeIds`, `callHandlerIds`, `chatRecipientIds`, `menu?` (shop items), `services?` (service offerings + prices), `products?` (goods for sale — a business can have products only, services only, or both), `rentals?` (`RentalItem[]` — things for rent, each with a price and a rental-catalog `subcategoryId`, priced per `rentalBasis`), ratings, `priceLevel`, `providerType`, `tags`, `openNow`, `distanceKm` (computed), etc.
- `Booking` — an appointment request: `businessId`, `customerId`, `serviceName`, `price?`, `when` (free-text date/time), `status: requested|accepted|declined|completed`. `ServiceItem`/`MenuItem`/`ProductItem` are `{name, price?, description?}` (`ProductItem` also takes `subcategoryId?`, set on personal-stall items, and `imageUrl?` — the photo the Stalls grid leads with; `MenuItem` also takes free-text `category?`/`subcategory?` — "Starters" → "Veg" — which drive the business page's collapsible menu).
- `Order` — a customer's cart-style request: `lines: OrderLine[]` (each `{kind: 'product'|'service', name, price?, quantity, included}`), `status: requested|proposed|accepted|rejected|declined`, `responseMessage?`, `respondedByName?`, `billId?`. The `included` flag is how proposals work: the business unticks lines it can't provide. All prices are free-text labels; `lib/money.ts` (`parsePrice`/`formatMoney`) does totals.
- `Bill` — issued by a business to a customer (auto on order acceptance, or by hand): `lines: BillLine[]` (`{name, quantity, price?, amount?}`), computed `total`, `issuedByName`, optional `customerId` (in-app delivery) and `orderId`.
- `Employee` — `businessId`, `displayName`, `role?`, `level: 'manager'|'staff'`, `userId?` (set if a registered user). Owner = `Business.ownerId` (a User), sits above all employees.
- `User` — `isProfilePublic` controls whether they're discoverable/tappable as an employee.
- `SavedPlace` — Current / Home / Work (kind), each with a `point`. Used by the location dropdown + distance sorting.
- `ChatMessage` — one thread PER customer PER business (`threadKey = businessId:participantId`). `authorType: 'customer' | 'business'`. Optional `billId` renders the message as a tappable bill card.
- `Call` / `CallParticipant` — a WhatsApp-style internet voice call to a business (no phone numbers exchanged). `status: ringing|active|ended|missed|declined`; each participant has its own `state: ringing|joined|left|declined` so group join/leave works. Ring targets = owner (unless `Business.ownerHandlesCalls === false`) + `callHandlerIds` employees **with an app account** (`userId` set).
- `AppNotification` — per recipient; created when a business replies in chat, on bookings, on missed calls, on order events (`order_requested`/`order_update`, deep-links via `orderId`) and manual bills (`bill_issued`, via `billId`).
- `Vehicle` / `TrackedItem` / `LocationShare` — live tracking. A `Vehicle` (bus/van/truck/…, kinds as data in `catalog.ts` → `VEHICLE_KINDS`) belongs to a business, is identified by its `registrationNumber` (number plate; `name` is the optional pet name, falling back to the plate) and has a `driverEmployeeId`; its live position IS the driver's `LocationShare` (per business, explicitly toggled on/off by the employee). A `TrackedItem` (`kind: 'child' | 'goods'`, e.g. a kid on the school run or a parcel) belongs to a `customerId` and rides on a `vehicleId` — the customer tracks their item by watching that vehicle.
- `Deal` — a live limited-time offer on a `Business` (`deals?`): `tag` ("40% OFF"), `title`, `price`/`wasPrice` labels, `emoji?`. Powers the Browse "Deals near you" carousel.
- `ProductMessage` — one post on a stall product's PUBLIC thread: `businessId`, `productId`, `authorId`/`authorName`, `fromSeller`, `text`, `offerPrice?` (present = it's a price proposal), `replyToId?` (hangs an answer under the question it answers). Read by everyone, posted by anyone signed in.
- `Review` — verified-customer rating: `businessId`, `customerId`, `rating` 1–5, `comment` (required ≤2 stars), `updatedAt?` on edit. One per customer per business.
- `PortfolioItem` — a piece of the work showcase on a `Business` (`portfolio?`): `kind: 'photo' | 'video'`, `url`, `thumbnailUrl?`, `title?`, `description?`.
- `MenuItem`, `GeoPoint`, `BusinessLocation` (privacy: `isHome`, `hidePreciseLocation`).

**Taxonomy note (tags-first):** discovery runs on **tags** — `Business.tags`, vocabulary + helpers in `src/domain/tags.ts` (`TAG_CATALOG`, `SUGGESTED_TAGS`, `hasTag`, `isFoodShop`). A business carries many tags (an MRF dealer is Tyres + Wheel alignment + Vehicle service) and appears under every matching filter; owners can also type custom tags. **Customer browse categories are `INTENT_CATEGORIES` in `domain/intents.ts`** (Food, Health, Home Services, Rentals, Stalls, … — each a bundle of tags); `ListingType` is now *internal-only* capability wiring (register flow shape, stall folding, rental basis) — never a customer-facing category; `subcategoryId` is legacy-but-alive: items still pick one (stall chips run on it), and for other types it's *derived* from tags when one matches (Cafe tag → `cafe`). `offersDineIn` is tag-aware. Don't key new features on subcategory — key them on tags or capabilities. The long-term model (customer marketplace + modular business workspace) lives in `docs/direction.md` — read it before big product changes.

Customer taps **🛒 Order** on the business page → `app/order/new/[businessId].tsx` (quantity steppers, note, running total; menu items group into the same category → subcategory dropdowns as the business-page menu, with picked counts on collapsed bars) → `requested` order. Full per-customer history in `app/orders/[businessId].tsx` (role-aware: member = all orders, customer = their own; reachable from the business page's "📦 My orders here" button). Customers ALSO get a **My Orders bottom tab** (`app/(tabs)/orders.tsx`): every order they ever placed across all businesses, grouped IN PROGRESS (requested/proposed, flags proposals awaiting their decision) vs PAST, refreshed on tab focus, rows tap through to the order. `OrderRepository`; totals via `features/orders/orderUtils.ts`.
- **Personal stalls (the "Stalls" tile)**: registering an `item` never creates a second listing — `BusinessRepository.create` folds the item into the owner's single stall (found via `getStallForOwner`), creating "‹Name›'s Stall" on their first item. Bill detail `app/bill/[billId].tsx` renders the invoice and shares it: **📤 Share** (`lib/share.ts` — native share sheet; Web Share API / clipboard on web) and **💬 Send in customer's chat** (`BillRepository.sendToChat` → bill-card chat message). All bills: `app/bills/[businessId].tsx` (members only). Text rendering in `features/billing/billText.ts`.
- **Customers & favourites**: `app/customers/[businessId].tsx` (members only, "👥 View customers" in the workspace) lists everyone who ever did business with the listing. Nothing is stored — `CustomerRepository.listForBusiness` aggregates live from orders, bookings, bills, chats and calls; a customer's `key` is their user id, `'guest'`, or `walkin:<name>` for hand-typed bill customers. The OWNER stars favourites (`setFavorite` → persisted on `Business.favoriteCustomerIds`), which pin to the top. Rows show activity counts + total billed and quick links to the chat / orders / new bill.

## Conventions

- New screen = new file under `src/app/`. Register it in `src/app/_layout.tsx` (for a title) if it's a stack route.
- Use theme tokens from `@/theme/theme` (`useColors()`, `spacing`, `radius`, `fontSize`) — never hardcode colors.
- Use UI primitives from `@/components/ui` (`Text`, `Button`, `Card`, `Input`, `Tag`, `Screen`, `Avatar`, `Stars`, `SearchIcon`, `ScanIcon`, `LoadingView`/`ErrorView`/`EmptyView`).
- Data fetching: `useAsync(() => repos.x.y(), [deps])`.
- Keep the app **dynamic** — render from repository data, avoid hardcoded IDs/lists.

## Run & verify

- Install (this repo needs it): `npm install --legacy-peer-deps` (a peer conflict blocks plain `npx expo install`).
- Run: `npx expo start --web` (browser preview at http://localhost:8081) or `npx expo start` (Expo Go). In this CLI you can also do `! npx expo start --web`.
- Verify a change: `npx tsc --noEmit` AND `npx expo export --platform web` (both should exit 0).
- **Typed-routes gotcha**: after ADDING a new route file, `.expo/types/router.d.ts` only regenerates while the **dev server is running** — and an ALREADY-RUNNING server regenerates new **dynamic** routes wrongly (as a literal `/foo/[id]` string instead of `/foo/${SingleRoutePart}`, so `router.push(\`/foo/${x}\`)` fails tsc; it may also emit bogus non-route entries). Fix: kill the server, delete `.expo/types/router.d.ts`, start a fresh server, wait ~45s, re-run `tsc`.

## What's mocked / deferred (don't assume these exist)

- **No real backend** — in-memory mock, resets on reload. Auth is mocked (any credentials sign in as the demo user).
- **Current location uses real GPS** (`expo-location`, behind `PlacesRepository.getCurrentPlace`/`listPlaces` via `lib/location.ts`) — it requests permission and reads the device position, falling back to the seeded `CURRENT_POINT` (Indore, seed.ts) when permission is denied or GPS is unavailable. On web, geolocation only works over `https://` or `localhost`.
- **Map is schematic** (no street tiles) — real maps need a native dev build.
- **Call audio is simulated** — the UI polls `CallRepository` as a stand-in for realtime signaling. Real voice (WebRTC, e.g. LiveKit/react-native-webrtc) and ringing while the app is closed (VoIP push + CallKeep) require the real backend and a native dev build; both plug in behind `CallRepository` without UI changes.
- **Vehicle movement is simulated** — active `LocationShare`s random-walk near the business at an exaggerated speed (`advanceShares` in mockRepositories.ts) so the demo visibly moves; the tracking map polls every 3s. Real driver GPS (`expo-location` background updates on the driver's phone + a realtime channel) plugs in behind `TrackingRepository` without UI changes.
- **QR scanning is native-only** — expo-camera has no barcode support on web, so `/scan` on web (our preview) is a paste-a-link fallback. Real scanning works in Expo Go / a dev build.
- **Showcase media is URL-linked** — portfolio photos/videos are added by pasting a link; direct uploads (camera roll → storage) and inline video playback need the real backend.
- **Stall photos aren't uploaded anywhere** — `PhotosField` picks photos and stores the LOCAL uris (`file://` / `blob:`) on `ProductItem.images`, so they render for the session and die with the mock backend. Real storage slots in inside `PhotosField` (pick → upload → keep the returned URLs); no caller changes.
- **Bill "PDF" sharing is text for now** — `lib/share.ts` sends a formatted plain-text bill through the system share sheet (clipboard fallback on web). Real PDF rendering (e.g. `expo-print` + `expo-sharing`) plugs in behind the same share button once the real backend exists.
- **Deferred by user request**: the business-facing "IT services" layer (inventory management, vehicle/fleet tracking). Context only — do NOT build until asked.
